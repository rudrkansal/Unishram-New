02

The SMS/OTP question — read this first

You asked me to prepare the "SMS permission justification." Good news: there isn't one to write.

Why no SMS permission exists

I checked the manifest directly — READ_SMS and RECEIVE_SMS are not declared anywhere. The app authenticates phone numbers through Firebase Phone Auth, which uses Google's permission-less SMS Retriever API to auto-detect the OTP code. Android grants that mechanism access to exactly one incoming SMS matching an app-specific hash, without your app ever holding a general SMS-reading permission.

This matters because Play Console's Restricted Permissions review (the one that can ask for a justification video and add days to your review) is triggered specifically by declaring READ_SMS / RECEIVE_SMS in the manifest. Since this app doesn't declare them, that entire extra review step does not apply to you.

One thing to verify yourself: if you ever add a package like sms_autofill or similar later, double-check it doesn't silently add RECEIVE_SMS to the merged manifest — some autofill plugins do. Run flutter build apk --release and check the final merged manifest in build/app/intermediates/merged_manifests/release/AndroidManifest.xml before every submission if you're unsure.

ℹ
On "Shared": Firebase Analytics and Crashlytics send data to Google as the service provider running your backend. Play's form has a specific carve-out for this — when you select these SDKs, the form auto-flags them and generally expects "shared" only if the data leaves Firebase for a purpose beyond running the app (e.g. advertising). You're not using Firebase for ads, so when the form asks "is this data shared with a third party," most developers correctly answer No for the core Firebase services, since Google acts as your data processor, not an independent third party. Analytics/Crashlytics still need to be declared as collected either way. If you're unsure, Play Console's in-flow help text next to each SDK explains this — read it at submission time since Google updates this guidance periodically.

Standard follow-up questions

Is all of the user data collected by your app encrypted in transit?
Yes — all traffic goes through Firebase over HTTPS/TLS.
Do you provide a way for users to request that their data be deleted?
Yes — the app has an in-app "Delete Account" action (Profile → Delete Account) that removes the user's account.
Is data collection required or optional?
Required for name, phone, and role — the app cannot function as a job marketplace without them. Location, photos, and voice control are optional / permission-gated at the OS level.
04

Privacy policy requirements

A live, publicly reachable Privacy Policy URL is mandatory before you can submit — Play Console will refuse to publish without one.

What it must cover, given what this app actually does

  • What personal data is collected: name, phone number, location, photos, chat messages, ratings/reviews
  • That phone number is used for OTP sign-in via Firebase Authentication
  • That location is used to show nearby jobs and is not collected in the background
  • That Firebase (Google) is the data processor, and name the specific services used (Auth, Firestore, Storage, Analytics, Crashlytics, Cloud Messaging)
  • How a user can request account/data deletion (point to the in-app Delete Account flow)
  • A contact email for privacy questions
  • Last-updated date
⚠
You need a URL, not a document. Play Console specifically requires a hosted, publicly accessible link — a Google Doc set to "anyone with the link," a simple page on your own domain, or a free privacy-policy generator page all work. It just has to resolve for Google's reviewers without a login.
05

Pre-submission checklist

Everything above, as one list to work through before you hit "Send for review."

  • Delete the stale "Aadhaar card scanning" comment from AndroidManifest.xml (cosmetic, but avoids an unnecessary reviewer question)
  • Privacy Policy page live at a public URL
  • Data Safety form completed in Play Console using the answer key in Section 03
  • Permission justifications pasted in where Play Console asks for CAMERA / RECORD_AUDIO / LOCATION (Section 01)
  • App signed with your release keystore, versionCode bumped from the last submitted build
  • Store listing: screenshots, short description, full description, feature graphic
  • Content rating questionnaire completed (Play Console → Policy → App content → Content ratings)
  • Target API level meets Play's current minimum (check Play Console's own warning banner — this changes yearly)
  • Test the release build (not debug) end-to-end one more time — OTP sign-in, job posting, chat, rating
Given your account is already approved and has published before: if everything above is ready when you submit, expect review to land on the faster end — typically a few hours to 2–3 days. The two things most likely to slow it down are an incomplete Data Safety form and a broken/missing Privacy Policy link, both of which are covered above.
